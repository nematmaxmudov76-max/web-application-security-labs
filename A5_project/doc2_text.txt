A5. Inyeksiya zaifliklari: SQL inyeksiya, NoSQL va ORM xavfsizligi
Asosiy maqsadUshbu A5 laboratoriya mashg‘ulotining asosiy maqsadi — talabalarda veb-ilovalarning ma’lumotlar bazasi bilan aloqa qiluvchi qatlamlarida (Database Abstraction Layer) yuzaga keladigan Inyeksiya (Injection) zaifliklarini amaliy tushunish, ularni ekspluatatsiya qilish, sabablarini tahlil qilish hamda zamonaviy dasturlash standartlariga muvofiq xavfsiz holatga keltirish ko‘nikmalarini shakllantirishdir.
Laboratoriya davomida:
Foydalanuvchi kiritgan ma’lumotlar (Input) dastur kodi va ma’lumotlar bazasi so‘rovi (Query Structure) tuzilishini qanday o‘zgartirib yuborishini tajribada isbotlash. 
Relyatsion ma’lumotlar bazalarida xom SQL (Raw SQL) va string formatlash (f-string, konkatenatsiya) qanday xavf tug‘dirishini ko‘rsatish. 
ORM (Object-Relational Mapping — SQLAlchemy) kutubxonasidan foydalanishning o‘zi avtomatik tarzda xavfsizlik kafolatini bermasligini (ORM ichida xom SQL bajarish xatosi) ochib berish. 
NoSQL (MongoDB / mongomock) ma’lumotlar omborida matn (String) o‘rniga JSON obyektlari (Object / Dictionary) yuborilganda so‘rov mantig‘i qanday buzilishini (Operator Injection) tahlil qilish. 
Har uchala zaiflikni to‘g‘ri himoya usullari: parametrli so‘rovlar (Parameterized Queries / Prepared Statements), ORM model ifodalari hamda kiritma turini tekshirish (Type / Scalar Validation) orqali to‘liq bartaraf etish.

# Tuzatilgan sql_weak funksiyasi (Parametrli so'rov):
def sql_weak(name):
    with engine.connect() as conn:
        query = SQL + 'WHERE name = ? AND public = 1'
        return conn.exec_driver_sql(query, (name,)).mappings().all()
# Tuzatilgan orm_weak funksiyasi (Model ifodasi):
def orm_weak(name):
    with Session(engine) as session:
        stmt = select(Product).where(
            Product.name == name, Product.public.is_(True))
        return [dict(id=p.id, name=p.name, public=p.public)
                for p in session.scalars(stmt).all()]
# Tuzatilgan nosql_weak funksiyasi (Sxema va tur tekshiruvi):
def nosql_weak(body):
    if not isinstance(body, dict) or set(body) != {'name'}:
        abort(400, description='Faqat name maydoni kerak')
    name = scalar(body['name'])
    query = {'name': {'$eq': name}, 'public': True}
    return list(collection.find(query, {'_id': 0}))

Maxfiy yozuv himoyalangan
1-savol: SQLdagi ? placeholder nima uchun qo‘shtirnoqqa olinmaydi? (name,) oxiridagi vergul nimani bildiradi?
Javob: 
? belgisi SQL tahlilchisi (parser) uchun maxsus o‘rin egallovchi (placeholder) hisoblanadi. Agar uni WHERE name = '?' deb qo‘shtirnoqqa olsak, ma’lumotlar bazasi uni parametr emas, balki so‘roq belgisi shaklidagi oddiy matn literal deb tushunadi. Shuning uchun ? qo‘shtirnoqsiz yoziladi. 
Python tilida (name) ifodasi oddiy qavs ichidagi o‘zgaruvchi hisoblanadi (string turi). Oxiriga vergul qo‘yilgan (name,) sintaksisi esa Python’da bitta elementdan iborat kortej (tuple) yaratadi. Ma’lumotlar bazasi drayverlari parametrlarni kortej yoki ro‘yxat ko‘rinishida qabul qilishi shart. 
2-savol: Nega "O'quv qo'llanma" nomini rad etish (yoki apostrofni o‘chirish) to‘g‘ri himoya emas?
Javob:O‘zbek, ingliz va boshqa ko‘plab tillarda apostrof so‘zning ajralmas grammatik qismidir (masalan: O'quv, Ma'lumot, O'zbekiston, Don't). Agar tizim apostroflarni taqiqlasa yoki o‘chirib tashlasa: 
Foydalanuvchilar o‘z mahsulotlarini qonuniy nomi bilan saqlay olmaydi va qidira olmaydi. 
Bu xavfsizlik emas, balki tizim funksionalligining buzilishi (buzuq arxitektura) hisoblanadi.To‘g‘ri yo‘l — apostrofni o‘chirish emas, balki parametrli so‘rovlar orqali apostrofli matnlarni xavfsiz qayta ishlashdir. 
3-savol: session.execute(text(query)) qachon xavfli? Parametrli ORM ifodasi undan nimasi bilan farq qiladi?
Javob: 
session.execute(text(query)) funksiyasi, agar query o‘zgaruvchisi f-string yoki string konkatenatsiyasi (+) yordamida foydalanuvchi ma’lumotlari bilan birlashtirilgan bo‘lsa, o‘ta xavflidir. Chunki text() funksiyasi SQL matnini avtomatik xavfsizlantirmaydi. 
Parametrli ORM ifodasi (select(Product).where(Product.name == name)) esa obyekt darajasida ishlaydi. U foydalanuvchi kiritmasini SQL matniga qo‘shmaydi, balki drayver darajasida xavfsiz bog‘langan parametr sifatida uzatadi. 
4-savol: Nega NoSQL $ne:null sinovida 3 ta yozuv chiqdi, SQL OR sinovida esa 4 ta?
Javob: 
SQL inyeksiyasida buzg‘unchi oxiriga izoh (-- ) belgisini qo‘ydi. Natijada dasturchi yozgan AND public = 1 sharti butunlay bekor qilindi va hatto maxfiy bo‘lgan public = 0 yozuvi (ID=4) ham chiqdi (jami 4 ta). 
NoSQL kiritmasida esa foydalanuvchi faqat name maydoni o‘rniga obyekt yubordi. Lekin server kodi tomonidan belgilangan query = {'name': ..., 'public': True} filtridagi 'public': True sharti buzilmadi va saqlanib qoldi. Shu sababli NoSQL bazasi faqat public: True bo‘lgan 3 ta ochiq mahsulotni qaytardi, maxfiy ID=4 esa chiqmadi. 
5-savol: Parametrli so‘rov public kabi ko‘rinish shartining (ruxsat nazoratining) o‘rnini bosa oladimi?
Javob:Yo‘q, bosa olmaydi! Parametrli so‘rov — bu faqat so‘rov sintaksisini (tuzilmasini) buzilishdan himoya qiluvchi vositadir. Ko‘rinish sharti (public = 1) esa biznes mantiqi va ruxsat nazorati (Access Control) qoidasidir. Ular bir-birining o‘rnini bosmaydi, balki bir-birini to‘ldiradi. 
6-savol: Stored Procedure va "faqat xatoni yashirish" nega avtomatik himoya kafolati emas?
Javob: 
Agar Stored Procedure (saqlanadigan protsedura) ichida dinamik SQL (EXECUTE IMMEDIATE yoki sp_executesql) formatlash orqali yozilgan bo‘lsa, inyeksiya xuddi oddiy so‘rovdagi kabi sodir bo‘laveradi. 
Xato xabarlarini yashirish (masalan, foydalanuvchiga faqat HTTP 500 yoki umumiy xato ko‘rsatish) zaiflikni tuzatmaydi, balki faqat uni ko‘rinmas qiladi. Tajribali buzg‘unchi "Blind SQL Injection" (mantiqiy yoki vaqtga asoslangan inyeksiya) usullari orqali ma’lumotlarni o‘g‘irlashda davom etaveradi.
